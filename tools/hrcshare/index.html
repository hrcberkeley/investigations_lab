Send a file directly, with no server in the middle

HRC Share moves a file straight from your browser to the other person's browser. The file is never uploaded to any server, never stored anywhere, and never passes through HRC or anyone else. You connect by swapping two short codes.

⚠ Before you rely on this, understand what it does and doesn't protect
HRC Share keeps your file off the cloud and encrypts it while it travels between the two browsers. It does not make you anonymous or protect the file once it arrives. In particular:
  • The codes are the weak point. Send the invite and reply codes over a channel you already trust (an encrypted messenger). Anyone who can intercept and alter both codes could insert themselves into the transfer.
  • Your network address is exposed. The two devices reveal their IP addresses to each other (and to a third-party lookup service) so they can connect. This is private, not anonymous. It is not Tor.
  • The received file is unprotected. It arrives as an ordinary, unencrypted file on the other person's device, which may be backed up, shared, compromised, or seized.

How HRC Share works

The short version

When you send a file with most tools, the file is uploaded to a company's server, sits there for a while, and the other person downloads it from that server. The company, in principle, has your file.

HRC Share does not work that way. Your file goes directly from your browser to the other person's browser, over a private connection the two browsers build between themselves. Nothing is uploaded to a server, no account is needed, and HRC Share keeps no server-side copy or account state.

Because there is no server holding the file, there is no central copy for anyone to subpoena, leak, hack, or quietly scan. The file exists only on the two devices at the two ends. (That also means the protection ends at those two devices, which the security section below covers.)

How the connection gets made

The one tricky part is that two browsers don't normally know how to find each other across the internet. Most tools solve this with a "matchmaker" server. HRC Share avoids even that by having the two people do the introduction by hand. That's the two codes you copy and paste:

  1. The sender picks a file. Their browser writes an invite code, a block of text describing how to reach it.
  2. The sender passes that code to the receiver (over whatever channel they already trust).
  3. The receiver pastes it in, and their browser writes a reply code describing how to reach them.
  4. The receiver sends the reply code back. The sender pastes it and clicks Connect.
  5. Now each browser knows how to reach the other. They open a direct, encrypted channel and the file streams across it.

Those two codes are the introduction. Once they've been swapped, the browsers talk only to each other.

Classic and hardened lanes

The classic lane keeps the original flow: after the invite and reply codes are pasted, the transfer starts as soon as the browser connection opens. This is fastest, but it relies completely on the channel used to exchange the codes.

The hardened lane adds one more stop before the file moves. After both codes are exchanged, both browsers hash the offer and answer together and display the same short verification code. Both people should compare that code over a trusted second channel. If an attacker changed the connection codes in transit, the verification code will not match. This still depends on a comparison channel the attacker cannot silently edit.

Security caveats: please read this part

HRC Share gives you two real protections: your file is never placed on a third party's server in the cloud, and the connection between the two browsers is encrypted while the file travels (using a web standard called WebRTC, which encrypts the link automatically). Those are meaningful. They are also the limit of what this tool does. It is important to be clear about what it does not protect against, so you can decide whether it fits your situation.

Short version: HRC Share keeps your file off the cloud and scrambles it in transit. It does not make you anonymous, does not verify who is on the other end, and does not protect the file once it lands on the other person's device.

1. The codes you swap are the real trust anchor. The encryption keys that secure the transfer are carried inside the invite and reply codes themselves. In the classic lane, the security of the whole transfer rests on the channel you use to exchange those codes. If someone can intercept and alter both codes in transit (a classic interception attack), they can quietly substitute their own and end up sitting in the middle of your transfer, able to read the file while each side believes they are talking to the other. The hardened lane helps catch this by showing a shared verification code before transfer, but only if both people compare that code through a channel the attacker cannot silently edit.

2. Your network address is exposed, so this is private but not anonymous. For two browsers to find each other, each side learns the other's IP address, and a free public "address lookup" service (called STUN) also sees your IP. Your file's contents stay hidden, but someone observing the network (an internet provider, a network administrator, a well-resourced adversary) can generally see that your device connected to the other device and roughly how much data moved. If hiding the fact that two parties communicated, or hiding your location, matters for your safety, this tool is not the right choice and you should look at something built for anonymity, such as tools that route over Tor.

3. There is no check on who is at the other end. Nothing in HRC Share verifies the identity of the person you are connected to. You are trusting that whoever gave you the code is who you believe them to be. The tool cannot confirm that for you.

4. The received file is unprotected once it arrives. The encryption applies only while the file is in transit. After it lands, it is an ordinary file sitting on the other person's device, with no protection of its own. That device might be backed up to a cloud service, shared with others, infected with malware, or physically seized. The same is true of your own copy. If the file is sensitive, consider encrypting it yourself (for example in a password-protected archive) before sending, and share the password separately.

5. Everything depends on both devices being trustworthy. No transfer tool can protect against a compromised device. Malware, a keylogger, a malicious browser extension, or screen-recording on either end defeats the protections described here. Keep both devices as secure as you can.

6. No delivery guarantee. If the connection drops partway, the transfer simply fails; there is no resume and no copy held anywhere to retry from. You would start over.

If, after reading this, the tradeoffs fit what you need (sending one file to one person you are already in contact with, without handing it to a cloud provider), HRC Share does that job well. If they don't, that is exactly the kind of judgment this section is meant to help you make.

Other limits

This direct approach can fail on some heavily restricted networks (certain corporate or institutional firewalls) where the two browsers simply cannot reach each other without a relay, which this no-server version deliberately does not include. It also handles one file per session. For most situations, sending one file to one person you are already in contact with, it works well.
